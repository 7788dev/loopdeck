# Agent Note: 任务日志详情文案由 TaskMessage 模板组装

Status: implemented

## Problem

运行日志的"执行详情"文案由两个适配器各自手写，同一列表里混着三种文体：
`|键=值` 半结构化串（`音乐合伙人评分完成|本次提交=3|进度=服务端已确认`）、
排障式统计串（`本次内部批次 2 | 本次上报 300`）和"请求成功"这类零信息短语。
多子项任务（音乐人、云贝、VIP 成长、B 站聚合任务）的失败组合如果逐个硬编码，
组合数会随子项数量爆炸；且部分失败无重试机制，文案却习惯性承诺"重试"。

## Decision

- 新增 `app\service\TaskMessage`：适配器只上报结构化子项
  （label + status：done/already/none/skipped/failed，可选 retry、text 覆盖），
  句子由模板拼装——完成项合并、已办项合并、失败项套 `{label}失败`。
  多子项结果禁止手写整句。
- "将自动重试"后缀只在 `retry` 为真时出现。审计结论：全项目只有两类分钟级
  重试——结果携带 `retry_after_seconds`（打卡待核验、评分可重试失败）与
  调度租约未推进（异常路径）。其余失败由次日定时计划兜底，文案不得提重试；
  不为没有重试机制的任务补造重试机制。
- 面向用户的详情不承载排障信息：内部批次、拒绝码、上游失败原因、NCBL 确认
  细节等下沉到结果 `data`（如 daka 的 `internal_batches`/`rejections`/`reason`、
  评分的 `failures[].reason`）。
- 文案语体对齐大厂产品文案：`已/将/暂无/余额` 词汇系、`；` 分隔独立子任务、
  不用竖线键值对、不写"请求成功"。前端列名同步改为"状态/执行详情"。

## Alternatives considered

- 每种失败组合硬编码一条字符串：组合数 O(2^n)，新增子项要改多处，被否决。
- 在文案里保留上游原始报错便于排障：用户可读性差；原因下沉 `data`，通知与
  排查仍可取到，被否决。
- 给无重试机制的任务补一个统一重试机制再统一写"将自动重试"：改变调度行为、
  超出文案改造范围，且用户明确要求不新增机制，被否决。

## Consequences

- 适配器消息改为面向用户的短句后，依赖完整句子做断言的测试改为断言 `data`
  字段（如评分失败原因断言 `failures`）。
- `TaskMessage::compose` 的输出契约（无竖线、无"请求成功"、重试后缀条件化）
  由 `tests/TaskMessageTest.php` 钉住。
- 新增平台子任务时：登记 label 与 status 即可获得正确组合文案。
