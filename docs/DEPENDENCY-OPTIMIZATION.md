# v1.2.1 依赖优化与验证

## 选型与兼容性

本次以 `e419ae3` 为基线，优先优化通知路径中的重复加载、SMTP 建连和认证。运行环境继续要求 PHP 8.1+，容器保持现有 PHP 8.2 与 MySQL 8.4。

| 候选 | 结论 | 依据 |
| --- | --- | --- |
| PHPMailer 7.1.1 | 采用，Composer 精确锁定 | 官方项目列出 WordPress、Drupal、Joomla、SugarCRM 等使用者；兼容现有 SMTP、STARTTLS、SMTPS、UTF-8 与 PHP 8.1。替换手工拷贝的 6.6.0，后续更新进入依赖审计。批次复用降低处理开销和连接数。 |
| Symfony HtmlSanitizer 6.4.45 | 本次不采用 | PHP 8.1、DOM 扩展与 API 兼容，可按 HTML 白名单及链接协议清洗内容；但解析和内存成本明显增加，进程内缓存命中仍慢于基线，不符合本次性能要求。 |
| 现有 Guzzle 7.15.2 | 保留并延迟初始化 | 排队、关闭通知、仅使用邮件时不创建 HTTP 客户端，避免无效加载；HTTP 发送仍复用同一客户端。 |
| Redis、额外队列或常驻服务 | 不增加 | 当前为单机任务面板，没有证据表明新增常驻进程能改善此路径；保持现有数据库队列、独占认领与重试语义。 |

官方资料：

- [PHPMailer 项目、兼容性与使用者](https://github.com/PHPMailer/PHPMailer)
- [PHPMailer 批量发送与 SMTPKeepAlive](https://github.com/PHPMailer/PHPMailer/wiki/Sending-to-lists)
- [Symfony 6.4 HTML Sanitizer](https://symfony.com/doc/6.4/html_sanitizer.html)
- [Composer 锁定安装、平台校验与审计](https://getcomposer.org/doc/03-cli.md)

SMTP 主机、端口、用户名、密码和发件站点名共同决定连接身份。凭据或站点名变化会关闭旧连接；无关站点配置不参与计算。每封邮件清理全部收件人、附件和自定义头；失败、断线与批次结束均有回收或重连路径。保留 TLS 证书校验、发送超时及管理员邮件开关。

## 本地基准

环境为 Windows、PHP 8.1.34 CLI、Composer 2.10.2，两套独立工作树分别执行锁定依赖安装。每个场景使用独立 PHP 进程，交替运行基线和候选各 7 轮，以下为各轮结果的中位数。SMTP 使用同一离线协议夹具，执行实际 PHPMailer MIME 与发送代码，不连接外部服务器，也不人为添加网络延迟。

| 场景 | 基线 | 候选 | 结果 |
| --- | ---: | ---: | --- |
| 200 封邮件处理累计耗时 | 130.46 ms | 73.18 ms | 下降约 44% |
| 200 封邮件连接 / 认证次数 | 200 / 200 | 1 / 1 | 减少 99.5% |
| 空闲通知对象首次创建 | 10.10 ms | 0.42 ms | 减少无效 HTTP 客户端加载 |
| 空闲通知对象场景 PHP 峰值分配 | 4 MiB | 2 MiB | 下降 50% |
| 重复读取版本号，每次中位数 | 86.7 μs | 0.1 μs | 避免重复文件读取 |
| 原 HTML 热路径，每次中位数 | 4.4 μs | 4.4 μs | 保持原实现 |

未采用的 Symfony 方案在同一 1,337 字节 HTML 场景中，未命中缓存的解析中位数从约 4.3 μs 增至 479.5 μs，热路径从约 4.4 μs 增至 5.9 μs，首次加载及解析约 10 ms。不能用缓存命中的结果掩盖首次成本，因此本次移除该候选。

这些结果只说明所测路径，不能替代真实服务器的页面延迟、吞吐量或第三方 SMTP 网络测试。PHP 峰值分配不是整个容器 RSS；实际服务器需要同镜像、同资源限制的对照验证。

复现单场景：

```bash
php tests/RuntimeEfficiencyBenchmark.php transport 5000
php tests/RuntimeEfficiencyBenchmark.php smtp 200
php tests/RuntimeEfficiencyBenchmark.php version 5000
php tests/RuntimeEfficiencyBenchmark.php html_hot 5000
```

对比旧工作树时，将 `LOOPDECK_BENCHMARK_ROOT` 指向已执行 `composer install --no-dev` 的旧代码目录，并仍运行新版基准脚本。脚本兼容旧邮件命名空间，不访问数据库或外部 SMTP。

### 本机 TCP / STARTTLS 验证

另用只监听 `127.0.0.1` 的 SMTP 接收端，进行真实 TCP、TLS、认证及 SMTP 命令交互。临时测试证书被显式信任，客户端仍校验证书和主机名。交替执行三轮，每轮 200 封，旧版耗时中位数 3,289.89 ms，新版 260.47 ms，下降约 92.1%；连接、TLS 握手及认证次数均从 200 降到 1，投递内容及收件人校验零错误。此结果属于本机网络，不代表生产 SMTP 延迟。

候选连续处理 5,000 封本机邮件，耗时 5.76 秒、零错误、1 次连接/握手/认证，PHP 峰值分配 4 MiB；第 21 封预热后到最后一封，堆占用增长 8 字节。该有界压力验证没有发现随邮件数线性增长的内存占用，不等同于长期生产稳定性验证。

可选复现工具仅用于测试，需 Python 3 和 `cryptography`，不增加 PHP 生产依赖：

```bash
python tests/smtp_loopback_fixture.py --baseline /path/to/old-checkout
python tests/smtp_loopback_fixture.py --messages 5000 --rounds 1
```

## 验收

- 本地 36 个离线测试通过，覆盖平台任务、调度、通知、权限边界和更新器。
- 新增覆盖：收件人隔离、凭据轮换、无关配置变化、无效地址、SMTP 拒绝、断线恢复；批次正常或异常结束时关闭连接；单用户总览失败后其余消息继续处理；邮件模板只选取昵称。
- 使用 `composer validate --strict --no-check-publish`、`composer check-platform-reqs --no-dev` 与 `composer audit --locked --abandoned=fail` 检查锁文件、PHP 扩展及已公布的安全公告。
- Windows 检出的 Compose 文件可能使用 CRLF；更新器测试统一换行后再检查，避免把换行差异误判为配置错误。
- GitHub 镜像构建继续在 PHP 8.2 环境执行离线测试，目标架构为 `linux/amd64` 与 `linux/arm64`。生产验证须另行记录实际镜像摘要、请求结果及资源指标。

## 数据保护与部署顺序

本次不包含数据库表引擎、认证字段或业务数据迁移；原工作区中其他未提交修改独立保留。操作前确认实际 Compose 项目目录、项目名、镜像及卷名，不按默认名称猜测。

1. 只读盘点：记录健康状态、镜像 ID/摘要、Git 提交、卷挂载、空间余量及 CPU/内存基线。候选先推送独立分支；生产备份与验证完成前，不更新自动更新器读取的 `main` 版本。
2. 备份：短暂暂停自动更新器、调度器与应用写入入口，确认任务结束。备份项目数据库、完整应用数据卷（配置、账号状态、会话、上传文件）、宿主机 Compose/.env 与原代码状态；使用仅 root 可读的目录并生成校验和。旧库含 MyISAM 表时，不能只依赖 `--single-transaction`，须在停止写入后使用一致性锁备份。
3. 恢复验证：在独立网络、独立数据库及应用卷恢复副本，比较表清单、每表行数和内容校验，核对配置、上传文件及账号状态。副本停用调度、自动更新及外部通知，不向真实用户发送测试邮件。
4. 对照测试：在同一服务器使用旧、新镜像及独立测试数据验证登录页、权限拒绝、通知和任务回归；运行相同基准及有界并发测试，记录错误率、延迟、峰值资源与时长。有明确回退则停止发布。
5. 切换：保留旧镜像的回滚标签，保存可执行回滚命令。使用已验证的镜像摘要，只更新 `app`、`scheduler`、`updater`，保持原项目名、数据库容器与持久化卷。健康、版本和数据核对通过后恢复正常调度。
6. 回滚：候选失败时停止应用服务，用旧镜像重建这三个服务，保留数据卷。禁止删除卷、清库或覆盖现有数据。备份用于独立恢复与校验，不直接覆盖已接收新写入的生产数据库。

完成后保存备份位置、校验和、旧新镜像摘要、回滚脚本、实际测试结果和恢复调度时间。凭据、数据库内容、生产日志与备份归档不得提交 Git。
