# Agent Note: 打卡核验运行确认入账时报真实听歌总数

Status: implemented

## Problem

`daka_new` 的提前返回分支（进入时当日进度已达标）对所有场景一律返回
「今日已完成，无需重复打卡」。当上一轮上报已被网易云受理但计数尚未入账、
由调度器重试轮确认入账时，[重试中] 日志被
`Common::shouldReportTaskStatus()` 与 `TaskLogs::visibleLogsQuery()` 过滤，
当天唯一可见日志就只剩这句"无需重复打卡"——用户会误以为当天打卡根本没执行。
2026-09-25 线上实况：09:04 上报 360 首（[重试中] 被过滤），09:10 核验轮
入账 300 首，日志却只有一句"今日已完成，无需重复打卡"。

## Decision

- 提前返回分支按进入时的当日状态分流：
  - 当日状态 `completed=false`（或字段缺失）→ 本次是核验确认运行，文案与
    正常完成分支同句式、报真实数字：`本次已听歌 X 首，累计听歌总数由 Y 首
    变更为 Z 首`。X = 当前确认计数 - 当日基线（真实入账数，不为 300 写死），
    Y/Z = 当日基线与当前确认计数；`listen_songs_before/after/delta` 负载
    同步取真实值，`skipped_duplicate=false`、`verification_only=true`。
  - 仅当进入时当日状态已 `completed=true`（当天已完成后的手动补签或重复
    触发）才返回「今日已完成，无需重复打卡」，`skipped_duplicate=true`。
- 完全失败（核验窗口结束、达到每日上报上限等）的文案与 [失败]/[重试中]
  状态语义不变。

## Alternatives considered

- 恢复 [重试中] 日志落库/展示：重新引入等待噪音，违背"当日只留终态日志"的
  过滤决策，被否决。
- 核验确认文案写死 300：上报带安全余量、入账数会偏离 300（且含用户自听），
  写死失真，被否决。
- 改由 `app\service\TaskMessage` 模板拼装：打卡是单结果任务，数字来自当日
  状态文件而非子项状态集合，不适配子项模板，维持适配器组装，被否决。

## Consequences

- 用户凭当天唯一一条 [成功] 日志即可看到真实完成数字，无需比对状态文件。
- `tests/NeteaseDakaSettlementTest.php` 固化两条断言：核验确认运行的文案与
  计数负载；当日已完成后的重复触发保持 no-op 且文案不变。
