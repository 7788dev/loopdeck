# Agent Note: 哔哩哔哩上报、到账与空奖励分别判断

Status: implemented

## Problem

线上每日经验日志显示「今日经验+0」，而随后查询的 B 站账本显示此前七天每天实际到账 50 点。经验日志有延迟，不能作为即时合计。同时复现了心跳返回 code=0、登录和观看仍为 false，却被总任务标记成功；空礼包、空礼物列表和没有应援团也被写成已领取或均已签到。

桌面客户端 1.17.9.4828 的内置播放器 4.9.85（revision 96806e61）对观看开始和心跳请求都签名 `w_*` 查询参数。原 SDK 只签视频详情。签名上报实测被接受，但不能把接受请求当作到账证据。

继续核查发现，凌晨首次上报约一小时后，登录、观看和大会员经验才出现在账户总经验与账本中；账本仍将它们记在首次上报时间，而不是后续 PC 客户端对照测试的时间。当日累计最终从 10122 增至 10172，六笔奖励合计 50 点。不能把与 PC 对照测试接近的到账时刻当作切换接口的因果证据。

## Decision

- [SDK](../../../../extend/bilibili/sdk/Client.php) 复用 WBI signer，为观看开始和心跳签名与请求体一致的 `w_*` 字段，建立设备会话并复用同一视频的开始时间。
- [工作流](../../../../extend/bilibili/Bilibili.php) 以每日奖励的明确布尔状态确认观看；历史记录上报成功不能抵消心跳失败。基础经验仅合计已确认的登录、观看及实时投币经验，不含独立的大会员任务，不以延迟账本推断当天零收益。
- [执行器](../../../../app/service/BilibiliTaskExecutor.php) 将未确认的观看、每日经验及大会员前置条件交给最多 24 次、间隔 300 秒的核验，覆盖两小时结算窗口。状态保存在原任务 data 的 `_bilibili_verification` 中，包含日期和次数；核验不重新观看或投币。到账、次数耗尽或跨日即清除状态，恢复正常日程。失败与重试标签仍由 Common 生成。
- 统一调度、旧调度和 CLI 都保留同一核验状态；全局直播间配置不回写到单任务配置。大会员还核对 `is_grant`；今日投币经验读不到时停止投币，避免按零计算而重复支出。
- PC 礼包、心跳礼物的空列表不能记作已领取。APP 旧接口没有奖励明细，只报告请求已提交；没有应援团与银瓜子不足保留真实原因。没有恢复已下线的主站分享或直播签到。

## Alternatives considered

**照抄社区客户端的成功日志。** 维护中的客户端也有请求成功即记经验的实现，不能证明实际到账。

**等待或累加经验账本。** 账本有分钟级延迟；阻塞 worker 会拖慢其他账号，固定等待也不能保证结算。按已确认的任务状态合计并明确不含大会员。

**未到账时反复上报。** 会制造额外观看和投币副作用。核验只读状态，大会员仅在前置条件确认且权益仍未领取时发出领取请求。

**切换到桌面专用 APP 协议。** 需要另维护客户端签名和设备参数，本次没有证明它能改善到账，保留现有 Web 认证边界。

**仅核验三次后判失败。** v1.2.25 的 15 分钟窗口短于本次真实结算延迟，v1.2.26 扩展为 24 次，仍只读和有界。

**新增状态文件或数据库列。** 原任务 data 足够保存有界核验状态，不增加迁移与账号删除清理负担。

## Consequences

状态暂未到账时会显示「重试中」而不是成功；核验窗口结束后仍未确认会如实失败，不承诺绕过上游结算或风控。空奖励会显示真实原因。部署不修改数据库结构、Compose 服务或环境变量。

[协议测试](../../../../tests/BilibiliSdkTest.php)、[工作流测试](../../../../tests/BilibiliWorkflowTest.php) 和 [调度数据库回归](../../../../tests/BilibiliSettlementTest.php) 覆盖签名与请求体一致性、历史上报掩盖失败、延迟账本、空奖励、禁止重复投币、只读重试、次数上限、跨日、最终成功与主调度持久化。

核验入口不限于观看与每日经验：`vipExperience()` 也要区分两种等待。**前置条件未满足**（权益 `state=2`，观看尚未到账）时，核验轮次只读地复查观看，一旦账本变为可领取，必须允许**首次**领取 POST。**领取已提交但未确认发放**时，后续轮次绝不再次 POST，只能靠账本 `state=1` 确认今日已领取，否则继续挂待核验。两种状态用任务 data 里的 `_bilibili_verification.claim_submitted` 区分并随每一次待核验结果保持（执行器写入，`normalizeConfig()` 白名单之外单独转发为 `claim_submitted` 配置），因此跨 5 分钟跳次不会丢阶段。该标记与 `attempt` 共用同一日期门：昨天的 `claim_submitted` 对今天的权益毫无意义，继承它等于把复现出的 bug 从日期边界重新引回来。

把两种等待合并成"核验轮次一律只读"是错的：首次执行常因观看未到账进入核验态，此时还没提交领取，之后的每一轮都被挡住，实测 1 次执行 + 24 次核验的领取 POST 总数为 0，当天最终失败——用户被自己的延迟账本永久挡住领取。
