# Agent Note: 哔哩哔哩每日投币跳过已投满视频，零投币记为失败

Status: implemented

## Problem

`coinAdd()` 按"随机热门"取热门榜第 1 页开头的视频逐个投币，遇到 34005
（该视频已达本账号投币上限）就结束循环，且只有"0 枚成功且收集到其他错误"
才算失败。热门榜隔天变化不大，前一天投过的视频第二天仍排在前面，首个请求
即 34005、循环直接结束。2026-09-27 线上实况：每日投币记为 [成功]「已投币
0/3 枚，硬币余额 881」，随后的每日经验任务显示「投币经验 0/50」。
"失败误报成功"此前在 v1.2.6（网易云音乐人任务与领奖）修过一次，这是第二次。

## Decision

[`extend/bilibili/Bilibili.php`](../../../../extend/bilibili/Bilibili.php) 的 `coinAdd()`：

- 投币直接遍历 `candidateVideos()` 的全部去重候选，不再逐个请求视频详情；
  "随机热门"先打乱热门列表，"关注列表"保持动态顺序。
- 上游错误码分三类：34005（已投满）、34002（自己的视频）静默换下一个候选；
  10003、34003、34004、-400 等单视频错误记录后继续，累计 3 个即停止；
  其余（-104 硬币不足、-101 未登录、-102 封禁、-111 csrf 等账号级错误）
  记录后立即停止。分类对照 BiliBiliToolPro `DonateCoinCanContinueStatusDic`
  与 bilibili-API-collect 投币接口码表。
- 单次运行最多发 10 次投币请求。
- 一枚未投成即返回 `code 0`，文案为 `投币失败：<首个上游原因>`，没有上游
  原因时为「候选视频均已达投币上限」；有成功时余额显示投币后的数值。

## Alternatives considered

- 维持遇 34005 即结束：正是 0/N 误报成功的根因，被否决。
- 本地持久化已投视频列表来预先排除：要新增按账号的状态文件和清理逻辑，而
  34005 本身就是免费的"已投过"信号，被否决。
- "关注列表"候选全部投满时回退到热门：会把硬币投给用户没选的 UP 主，违背
  所选渠道，改为如实报失败，被否决。
- 遇 34004（投币间隔太短）先 sleep 再重试：线上未出现过 34004，sleep 会拖慢
  同进程调度，暂按单视频错误处理，被否决。
- 投币前仍逐个请求视频详情校验：候选多备后请求量成倍增加，失效稿件由 10003
  兜底，被否决。

## Consequences

- 零投币运行显示为 [失败] 并触发失败通知，用户能看到真实原因。
- 候选大多已投满的最坏情况下，一次运行发 10 个投币请求。
- 观看任务同样经 `candidateVideos()` 取候选，"随机热门"下观看的视频也随机。
- `tests/BilibiliWorkflowTest.php` 固化：34005 跳过后补投、全部投满报失败、
  硬币不足与未登录立即停止、10003 后继续、10 次请求上限、余额扣减。
