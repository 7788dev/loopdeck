# Agent Note: 统一兑换会员时长与跨平台账号总数

Status: implemented

## Problem

管理员原先只能分别生成固定面值的会员码或配额码。用户需要一次配置会员天数和账号总数，任意平台组合都使用同一个上限，续期不能无限叠加账号名额。

## Decision

[RedemptionPlan](../../../../app/service/RedemptionPlan.php)统一验证会员天数、账号总数与预设套餐。新码只生成 bundle 类型，在原有 varchar value 字段存储两个整数的 JSON，不需数据库迁移。后台选择预设套餐时使用套餐权益并隐藏天数、账号总数输入框，仅选择“自定义”时显示这两项，切回自定义保留当前数值；会员天数 0 表示永久会员，账号总数 0 表示不限数量，两项均为 0 表示永久无限套餐。生成数量仍为 1–1000。

新码账号总数取现有总数与码内总数的较大值；会员从尚未到期的结束日续期，否则从当天开始。账号名额沿用永久有效，会员到期不删除已绑定账号。旧 vip / quota 码保留原有延长天数 / 新增名额语义，只兼容兑换，不再生成。

用户表用 quota=-1 表示不限数量，既有 quota=0 仍表示没有名额；永久会员保存为 MySQL DATE 可表达的 9999-12-31，与现有调度及登录有效期检查兼容。永久会员不再累加日期，有限套餐不降低已有永久或无限权益。若两项权益都没有变化，返回提示并保留未使用的兑换码。后台用户编辑通过“永久会员／账号数量不限”选项保存，前台显示权益文案，不展示存储标记。

[兑换](../../../../app/index/model/Kms.php)先锁用户再锁兑换码，认领与两项权益写入在同一事务内完成；任何失败整体回滚。批量生成也使用事务，防止生成一部分却返回失败。[账号保存](../../../../app/index/model/Accounts.php)使用同一个用户行锁和数据库中的实时上限，跨平台合计数量，防止旧会话或同时添加越过上限。

## Alternatives considered

- 各平台填写独立配额：管理员需要的是总数，不能把 7 个拆成固定的平台份额。
- 每次兑换累加总数：续费会无限增加名额，与套餐总数含义不符。
- 强制覆盖为码内总数：低档套餐可能降低用户已有名额，影响已有账号。
- 将旧码直接解释为总数：改变已发放兑换码的权益；旧码仍按原规则兑换。
- 新增字段并启动时改表：现有字段足以保存紧凑的双权益数据，避免为简单组合引入升级迁移与数据库权限要求。
- 将用户表的 0 直接解释成无限：会把未获赠账号名额的旧用户意外升级；仅兑换码输入采用 0=无限，用户表单独标记。
- 0 表示不调整权益：用户明确要求 0 表示永久／无限，组合码两项均按这一含义兑现；旧单项码的兼容分支不受影响。

## Consequences

新后台只有会员天数、账号总数和生成数量，无平台配额表单；详情与复制结果明确展示权益。续期不会累加总数，也不会降低已有更高上限。旧码保留且无需管理员转换。回归覆盖组合兑换、永久无限、有限套餐不降级、旧用户零名额、边界校验、旧码、重复兑换、失败回滚、跨平台总数和陈旧会话。
