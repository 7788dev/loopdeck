# Agent Note: 分析结论必须经过第二次真实验证

Status: implemented

## Problem

2026-10-11 的一次全项目问题审查中，10 条"发现的问题"里有 1 条是误报：声称通知发送层缺少 HTTP 超时，实际 `app/service/NotificationTransport.php:88`（pushplus/wxpusher `timeout 8.0 / connect_timeout 3.0`）、`app/service/BarkClient.php:60-61`（`connect_timeout 5.0 / timeout 10.0`）每个请求都带超时，容器侧 `docker/scheduler.sh:55` 还有 `--max-time 120` 兜底。误报根因：第一遍只 grep 了 `extend/` 目录没有查 `app/service/` 就下了结论——搜索范围本身错了，行号引用再精确也是错的。另一条把 `tests/SharedAccountLimitTest.php:29` 明确断言的有意行为（收款码占用账号配额）当成了缺陷。第二遍验证用扩大的 grep、可执行 PHP 片段和测试资产交叉核对后，才把结论修正为"8 条成立、1 条撤回、1 条降级"。纯阅读推导的结论（哪怕带行号）区分不了"看起来有问题"和"真的有问题"。

## Decision

凡是以"分析问题/查找问题"为目标的任务（代码审查、排障、安全审计、架构评估），**无论第一遍结论是如何得出的**——快速阅读推导、工具扫描，还是第一遍本身已经做过真实验证——最终报告前都必须再进行一次真实验证。第二轮不信任第一轮的任何中间产物：第一轮跑过的复现要重跑，第一轮引用的行号与搜索范围要重查。第一遍纯阅读得出的结论只是假设；第一遍的真实验证同样可能因方法或范围错误而结论错误（本轮误报正出自一次真实执行的 grep——它真的跑了，只是只扫了 `extend/` 一个目录）。第二轮按下列标准执行：

1. **能执行的必须执行**：过滤绕过、加锁时序、配置范围这类结论用真实运行的复现脚本证明（如本例中 `php -r` 实跑 `safe_html()` 证明 `&#106;avascript:` 穿透），不用"应该会被过滤"式的推测表述。
2. **不能执行的用重新精读 + 范围自查兜底**：引用精确 `file:line` 前，先确认结论依赖的搜索范围覆盖完整（全目录、全部入口、全部同名实现）；误报最常来自漏查一个目录或一个并行入口。
3. **先查测试资产再下"缺陷"结论**：被 `tests/` 断言钉死的行为是有意设计，只能作为设计事实报告或走文案/文档渠道反馈，不能标为 bug。
4. **"修复是否生效"与"问题是否真实"适用同一条标准**：修复落地后重放原始复现脚本（应不再成立）并运行离线回归套件（应全绿），两者都过才算修复完成；"应该已经修好"不是完成状态。
5. **验证中发现的误报必须在最终报告中显式撤回并写明根因**，不允许静默丢弃——撤回记录本身就是下一次分析的输入。

## Alternatives considered

**只对高危结论做二次验证，低危直接报告。** 输因：误报的代价不按严重程度打折（本轮误报恰好是中危结论，会直接误导修复优先级）；分级验证必然滑向"这条看起来不重要就跳过"。二次验证成本低（一次扩大的 grep、一段可执行脚本），全量验证可负担。

**把验证做成自动化 lint/CI 步骤。** 输因：分析结论是自然语言报告而非代码产物，没有稳定可机检的形态；可执行的部分本就该直接执行（见 Decision 第 1 条），不可执行的部分只能靠第二轮交叉核对，无法固化为流水线闸门。

**用全仓库 grep 代替人工阅读来"验证"。** 输因（作为补充手段保留，不作为验证本身）：本轮实践恰好证明 grep 范围自己就会出错。正确顺序是先扩大并确认搜索范围、再精读关键文件、最后用执行验证兜底，三者缺一不可。

**第一次已经真实验证过的结论免于二次验证。** 输因：二次验证的价值恰恰在于独立复核第一轮的方法与范围，而不只是复核结论——本轮误报正出自一次"真实"执行的 grep（命令真实运行了，但搜索范围漏了 `app/service/`）；免检等于让第一轮的方法论错误永远无人纠正。用户决策（2026-10-11）明确否决此豁免："哪怕第一次真实验证了，第二次也验证一下"。

## Consequences

买到：报告可信度显著提升——8 条成立的结论全部带可执行证据或复核行号，1 条误报在进入修复排期前被拦截。付出：分析类任务多一轮验证时间；报告需包含验证过程小节（哪些结论有可执行证据、哪些仅行号证据、哪些被撤回）。约束外溢：报告修复时必须附复现脚本 before/after 或回归结果；对既有测试钉死的行为，缺陷报告需先引用并讨论该测试。
